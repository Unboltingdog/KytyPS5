# File I/O completion and guest worker wakeups

This is a static analysis of the fork, not an observation of Gus's current dump. The guest chooses thread names such as `FaWorkerIo1`; the emulator has no `FaWorkerIo`-specific scheduler or wakeup implementation. Consequently, the fork alone cannot identify the condition-variable name used by each such worker or prove which guest function signals it. The batch 25 call trace is needed to associate the guest wait and wake sites.

## How a guest worker can sleep and wake

- Condition variables: `PthreadCondTimedwait`, `PthreadCondTimedwaitAbs`, and `PthreadCondWait` in `src/kernel/pthread.cpp` add the current `Pthread` to `PthreadCondPrivate::waiters`. `PthreadCondSignal` / `PthreadCondSignalto` select one waiter through `CondWakeWaiter`; `PthreadCondBroadcast` wakes all of them. A per-thread `cond_sequence` change makes the wait return, followed by `cond_cv.notify_one()` on the host.
- Equeues: `KernelWaitEqueue` in `src/kernel/eventQueue.cpp` enters `KernelEqueuePrivate::WaitForEvents`, which sleeps on the queue's host `m_cond_var`. `KernelEqueuePrivate::AddEvent` and `TriggerEvent` signal that host condition variable. A returned event is copied to the guest's `KernelEvent` array by `GetTriggeredEvents`.
- Submission waits: the APR `WaitCommandBuffer` and AMPR `AmmWaitCommandBufferCompletion` exports in `src/libs/libAmpr.cpp` both call `AprShared::CompleteSubmission`. That waits on `g_submission_cv` until the ID is marked complete. This path does not itself signal a guest condition variable or equeue.
- Synchronous filesystem calls: `KernelRead`, `KernelPread`, and `KernelPreadv` in `src/kernel/fileSystem.cpp` perform host I/O on the calling thread and return the byte count directly. They do not wake another worker.

## AMPR completion to guest wakeup

1. `AprShared::ResolveOnePath` resolves the guest path through `FileSystem::GetRealFilename`, caches the host path by file ID, and records its size. The batch 25 trace logs only the original guest path.
2. Guest command-buffer construction creates `ReadFileCommand` and, when requested, `KernelEventCommand` records. `QueueCommandBuffer` moves the records into the APR or AMM `CommandEngine`.
3. `CommandEngine::Run` selects a ready submission. A `WaitCommand` whose address/counter comparison is false remains pending. Otherwise `ExecuteCommand` runs one record at a time in guest-specified order.
4. `ReadHostFileToGuest` opens the host file, seeks, copies bytes into guest memory, closes the file, and returns the byte count and status. `WriteAddressCommand` and `WriteCounterCommand` use release stores; `IsWaitSatisfied` uses acquire loads.
5. A `KernelEventCommand` calls `KernelTriggerEvent` with `KERNEL_EVFILT_AMPR`. `KernelEqueuePrivate::TriggerEvent` looks up `(ident, filter)` and invokes `AmprEventTriggerFunc`, which publishes the current event or appends to `pending_events` if an earlier one is still pending. It then signals the equeue's `m_cond_var`.
6. A guest thread blocked in `KernelWaitEqueue` can now return the AMPR event. Any subsequent wakeup of `FaWorkerIo*` is guest code: the emulator does not directly connect AMPR completion to a `FaWorkerIo*` condition variable.
7. After the final command (or the first error), `CommandEngine::Run` writes the optional result buffer and calls `AprShared::SetSubmissionComplete`. That marks the submission boolean and signals `g_submission_cv`, allowing `CompleteSubmission` to return. It is a separate wakeup channel from the equeue event.

There is no Fios HLE implementation or registration in this fork (`src/libs` has no Fios source and no Fios `LIB_NAME` / `LIB_VERSION`). Therefore there is no emulator-side Fios completion-to-wakeup path to trace beyond the generic unresolved/HLE call record.

## Places where a completion or wakeup can be lost

- **Trigger before add:** `KernelEqueuePrivate::TriggerEvent` returns `KERNEL_ERROR_ENOENT` when `(ident, filter)` is absent. It does not latch a user event for a later `KernelAddUserEvent`. `KernelTriggerUserEventForAll` likewise skips queues where the ID is absent and returns `ENOENT` if none accepted it. `EQUEUE_TRIGGER*` records expose this directly.
- **Error before the event command:** `CommandEngine::Run` stops a submission on the first failed command. If a read or another earlier command fails, a later `KernelEventCommand` never runs. The submission result/completion flag is still written, so an equeue waiter and a submission waiter can observe different outcomes. Compare `AMPR_COMPLETE` with `EQUEUE_TRIGGER` and `EQUEUE_WAIT_RETURN`.
- **Wait command never satisfied:** a false `WaitCommand` leaves the submission pending and its completion/event records unexecuted. The engine polls every 100 microseconds because CPU/GPU fence writes do not notify its queue. `AMPR_SUBMIT` without `AMPR_COMPLETE` is the signature.
- **`EV_CLEAR` / delivery semantics:** user level events do not clear after delivery; `KernelAddUserEventEdge` sets `EV_CLEAR`, and `UserEventResetFunc` clears them. AMPR has a pending-event queue for completions arriving while an earlier event is undelivered. The generic reset path also honors `EV_CLEAR` when no filter reset callback exists. Wrong guest flags can therefore turn edge delivery into repeated level delivery or clear state after the first return. The wait-return trace includes flags and pending outcomes; the static code does not show which flags the guest intended.
- **Condition signal with no waiter:** `CondWakeWaiter` returns without changing state when the waiter list is empty, and broadcast of an empty list does the same. This is normal condition-variable behavior, not a persisted semaphore count. A guest that expects the notification itself to persist needs a separate predicate/counter. A signal after a selected waiter is removed but before it waits again is also not queued. `COND_SIGNAL*` records include `waiters=0` and `woken=-` for this case.
- **Unknown or already-consumed submission ID:** `CompleteSubmission` returns false immediately for an unknown ID, producing `ESRCH` in its HLE wrapper. After a completed ID wakes waiters, the first caller erases it; another waiter for the same ID can then erase nothing and return false even though the submission completed. The `AMPR_WAIT_BEGIN` / `AMPR_WAIT_RETURN` pair distinguishes this from a submission that never finished.
- **No allocated submission ID:** queue APIs without `out_submission_id` use ID zero and cannot be waited on through `CompleteSubmission`. Their equeue/result-buffer channels may still complete normally.

The OS-facing requirements exposed by these paths are reliable mount/path resolution and short-read byte counts, ordered command execution with visible release/acquire fence writes, event registration before triggers, correct edge-versus-level flags, and host condition-variable notifications tied to a guest-visible predicate. A condition-variable notification alone is not durable state.
